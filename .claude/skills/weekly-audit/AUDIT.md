# The weekly fresh-eyes audit: the Sunday procedure

Each Sunday one reviewer with no prior context reads the week's changed framework files, the lifecycle rows due for review, the items with no lifecycle row and one rotating slice. It explores first, then checks what it found against the known faults. The head re-verifies each finding and disposes of it. Design: section 2 of the waste-reduction and retirement design page (`wiki/developments/`), with section 3 for the lifecycle rows, as simplified by option S (the owner's choice of 12 October 2026): the order of the two passes is shown as the list of the reviewer's earlier commands, which the head reads and judges at step 6; no tool judges it.

The audit is a step of the owner's Sunday review, which he starts himself; nothing schedules it (his decision of 11 October 2026). The head starts it at the start of the review, so it runs while the calendar is walked.

## Files

- `slice.py` picks the slice and prints its reading list. With `--manifest-out` the pick also writes its manifest to that one path, once every acquisition has reported. With `--record` it records the audit in `slices.json` from that manifest and the reviewer's report. With `--init` it creates `slices.json` once, at install. The plain pick writes nothing. Every read the pick makes is a registered acquisition: each root's hash scan, the owed content, the rotation listing, the lifecycle rows, the inventory, the due rows' files, and the two comparison sources the second pass labels against (the register, and deep-lint's latest entry in `wiki/log.md`); and the requirement files, which reads nothing itself but vouches that each is there to read. One that fails, returns unknown or never reports makes the pick incomplete: it says so, reads what depends on it as UNKNOWN, marks its manifest incomplete and exits 3. An acquisition succeeds only on input whose structure is sound: text decoded strictly, never with replaced bytes, each Markdown input read by its protocol (Reading protocols, below: no fence, comment, list or quote can hide a line from the four raw readers, and the two section lists are read by markdown-it-py, which says UNKNOWN for what its declared syntax cannot decide), JSON whole, and a table or section read only in part counts as not read. Each acquisition names the structural rules it checks (the table `WHOLE_INPUT` in `slice.py`), and what structure cannot show is the limit of step 1. The pick also records every mandatory input of the audit in its manifest: the reading list and the requirement files (pass 1) and the second-pass sources (pass 2), any of which the reviewer's `## Not read` section may name, and which of them are comparison sources, whatever their phase (the register, a reading-list file in its own week, and `wiki/log.md`). A requirement file of the slice that is absent at the pick stays listed, so the report can name it, and leaves the pick incomplete, whatever else lists its path: when the reading list holds it already (as a deletion owed from an earlier audit, say), it stays there, not repeated, and its absence still leaves the pick incomplete. Every path the pick prints is spelled under the roots as they were given, a due row's files included. The second-pass sources (the lifecycle page, `wiki/log.md`, and the register unless it is the slice) never enter the reading list or the requirement files, whatever names them (a due row, an owed entry, a changed file). A path is absent only when its own metadata says so: an error looking at it is a failed acquisition, never "not there". The record's own acquisitions (the premises, `slices.json`, the manifest and the report) govern the recorded completion the same way, and the record writes the new state beside `slices.json`, reads it back and checks it, and only then replaces `slices.json` in one step.
- `pass_order.py` lists every command the reviewer ran before its first-pass message, from the reviewer's own run record: in the order each started, one entry per execution, verbatim, with the count and the record's path. It judges nothing and writes nothing. A record it cannot read whole gives `could not read` lines and no list; a record with no complete first-pass message says so and gives no list.
- `brief-audit.md` is the reviewer's brief template.
- `test_slice.py` and `test_pass_order.py` are the suites: each ends `PASS n/n`, or names each failure and ends `FAIL k/n`.
- `slices.json`, in `<store>/tools/weekly-audit/` outside the vault because this folder ships, holds the audit history (each audit marked complete or not, with each reason it was not), the hash baseline and the owed content. `--init` creates it at install. Never delete it to start over: the rotation and the changed-file list both depend on it, and once it is missing every pick and record refuses as a continuity failure.
- `slice.py` needs markdown-it-py 4.2.0 (`python3 -m pip install markdown-it-py==4.2.0`; the owner's decision D18 of 13 October 2026): it reads the section lists of CLAUDE.md and CUSTOMISATION.md, and nothing else. Missing, unimportable or of another version, it leaves the inventory UNKNOWN and every pick incomplete (exit 3), never a fallback to another reader.

## Reading protocols

The owner's decision D18: no hand-written Markdown structure reader. The four inputs where a misread would be silent are read on their raw lines, each line against a literal grammar, wherever it stands: a line inside a code block, a list item, a block quote or an HTML comment is read like any other, so nothing can hide a line from these readers, and an example that quotes a record's syntax at the start of a line is read as that syntax. `slice.py` states each protocol beside its code, to the same rules, and the suite holds a reading of each written apart from it, which must give the same verdict.
- **The reviewer's coverage section** (the report). Its record is the declaration. A declaring line is any `#` heading whose text begins with the words `Not read`, in any letter case, after any spaces, `>` marks or list markers; exactly one such line in the whole report is required, and it must be exactly `## Not read`. A closing line is any line whose first words are `end`, `not`, `read` (a path line, which begins with `/`, never is); exactly one is required, exactly `END NOT READ: <n>`, after the heading and the report's last line. Whole: between them only blank lines, the single word `none`, or mandatory paths, each with its exact characters, n the path lines (0 with `none`). Torn, so refused with nothing written: none or two of either line, a heading in another form, an empty section, a heading after it, a stray line, a miscount. Examples: a quoted, fenced or commented copy of the heading or of the END line is a second one, so the reviewer writes each once and nowhere else.
- **The lifecycle tables** (`wiki/developments/check-lifecycle.md`). A table line is any line whose first character other than a space or tab is `|`; its record is a row. A lifecycle table is the exact header, its separator of ten cells and whole rows; a header and separator alone is a valid empty table. Torn, so UNKNOWN: a header alone, a header over no such separator, a torn row, rows in no table, a damaged lifecycle header (ten cells, or a `Next review` cell, yet not the exact header), a table line inside a block quote. Examples: a row quoted at the start of a line, in a code block or not, is a row (of its table, or alone in no table, which is damage); an example row is written inside a sentence.
- **The register** (`wiki/developments/known-issues.md`). Its records are its two section headings, lines `## Open` and `## Closed`. Whole: exactly one of each, Open first. Torn, so UNKNOWN: either missing, either given twice, or Closed first. Examples: either heading quoted at the start of a line, in a code block or a comment too, is that heading (so the register is UNKNOWN); the entry template's `###` lines are no section heading.
- **Deep-lint's latest entry** (`wiki/log.md`). Its record is an entry: a heading line and the lines after it, up to the next line that begins with `#` after any spaces, `>` marks or list markers, a malformed heading or one behind a list marker included, so no field is borrowed from what follows. The latest deep-lint heading is the log's last line naming one in any form: after any such prefix, a `#` heading whose kind is deep-lint however written (`deep lint`, `deeplint`, any letter case), standing before the heading's first `|` or as its first word, whatever its date became (a bracket left open, another shape, none); a title naming deep-lint after the `|` names no deep-lint heading. It must be exactly `## [YYYY-MM-DD] deep-lint | <title>`, or the source fails, and no older entry is read in its place. Whole: its complete `- **Changed**:` and `- **Conflicts**:` fields, each followed by a value. Torn: a malformed latest heading, a heading alone, a field torn, misnamed or empty. Examples: a heading or field in its exact form counts wherever it stands. A latest heading damaged until its kind no longer names deep-lint before its title (one cut inside its kind, say) is no deep-lint heading: that is the limit of step 1, whose backstop is step 7's label check.
- **The section lists of CLAUDE.md and CUSTOMISATION.md** are read by markdown-it-py through one adapter in `slice.py`, the only code that imports it. Its declared syntax: a front matter at the file's start (its first line exactly `---`, to the next line exactly `---`) is set aside; the rest is parsed with the CommonMark preset; a section is a level-2 ATX heading (`##`) at the top level, in no list item or block quote. Every line that looks like one (`##` up to three spaces in, then a space, a tab or the line's end) must be a section or lie inside a fenced block markdown-it closed (an example). Anywhere else (the front matter, an HTML comment or block, a fence left open, a list item, a block quote), and for a setext or nested level-2 heading, the list is undecidable: the inventory fails for that file and the pick is incomplete, never a shorter list.

In the commands below, `<YYYYMMDD>` and `<YYYY-MM-DD>` are the review's date, `<vault>` is the vault root's absolute path and `<store>` is the run store (`LLM_WIKI_STORE`, else `~/.llm-wiki`). Write them out in full before running anything. `python3` is an interpreter holding markdown-it-py 4.2.0.

## Install

Once. `setup.sh` does step 1 on a fresh vault:
1. Create `slices.json`: `python3 -B <vault>/.claude/skills/weekly-audit/slice.py --init`
   First make its folders: `mkdir -p <store>/tools/weekly-audit <store>/hooks`. It prints `INITIALISED: <path> · no audits, no baseline`. It refuses when the file exists, so it never runs over the history.
2. Run each suite once: `python3 -B <vault>/.claude/skills/weekly-audit/test_slice.py` and `python3 -B <vault>/.claude/skills/weekly-audit/test_pass_order.py`. Each must end `PASS n/n`.

The section adapter in `slice.py` needs markdown-it-py 4.2.0 installed for `python3`; without it a pick reports the standing-rules inventory unknown and stays incomplete. The vault's part: the audit's lifecycle rows, which the first audit enrols, and the Sunday-review sentences in `CALENDAR.md`, which `setup.sh` seeds.

## Steps

Before step 1, take the first usage reading for the cost record (step 9), and keep its output with the time you took it:
`python3 -B <vault>/.claude/skills/delegate/read-usage.py --only both`

1. **Pick the slice.** Create the head's folder with `mkdir -p /tmp/run-<YYYYMMDD>-audit`, then run:
   `python3 -B <vault>/.claude/skills/weekly-audit/slice.py --vault "<vault>" --manifest-out /tmp/run-<YYYYMMDD>-audit/manifest.json`
   The manifest is the hash of every file as the audit reads it, its reading list and the outcome of every acquisition; step 10 records from it. Keep the output for steps 3 and 6, and read its exit code:
   - **0:** the slice printed, every acquisition succeeded (the `CONTROLS` line counts them), and its `manifest:` line says the manifest was written.
   - **3:** the slice printed, but the pick is incomplete: its `INCOMPLETE` block names each acquisition that failed, returned unknown or never reported, with what it could not read and what that leaves UNKNOWN (the changed files, the owed content, the rotation's choice and its files, the due rows, the missing rows, the labels), and the summary reads those results as UNKNOWN, never as none. A required root that was gone when an acquisition's walk read it is unread, and a root restored after the pick does not undo that: the manifest already holds the failure. A lifecycle page that is missing, unreadable (undecodable bytes included), without its table, or with a damaged one (a header alone, a header whose next line is not its separator, a torn row, rows cut off from their table, a damaged lifecycle header, a row inside a block quote: Reading protocols) makes the pick incomplete too (`DUE ROWS: UNKNOWN`), never "nothing due"; a header and separator with no rows is a valid empty table. Every source is read whole or not at all: undecodable bytes are never replaced, a file read only in part counts as unread, and a path that could not be looked at (a permission refused, say) is a failure, never absent, as is a symbolic link whose target is missing. So is a register without its `## Open` or `## Closed` section, or with either given twice or its Closed first, and a deep-lint heading whose entry lacks its complete `- **Changed**:` or `- **Conflicts**:` field, each followed by a value (a field torn, misnamed or with nothing after its colon is no field), or a latest deep-lint heading in another form (its bracket left open, its date in another shape, a list marker before it), in whose place no older entry is ever read. A standing-rules file whose section list markdown-it-py cannot decide, or markdown-it-py itself missing, leaves `MISSING ROWS: UNKNOWN`. A requirement file of the slice that is absent (`.claude/settings.json` in the hooks-and-monitors week) makes the pick incomplete too, whatever else lists its path: no reviewer can read it, and the REQUIREMENT FILES block still lists it, with a note, so that the report names it, or, when the reading list holds its path already (a deletion owed from an earlier audit, say), the note says so and the path stays there. A part of the reading list whose acquisition did not succeed says UNKNOWN in its header, never a bare count. When the register or deep-lint's entry could not be read whole, the SECOND-PASS SOURCES block says `LABELS LIMITED`: no finding of this audit can be labelled `new kind` (step 7). Mend what it names if you can now (a permission, a file mid-sync, a folder mid-move) and pick again. Otherwise go on with this incomplete pick: what it could not read is a finding of this audit for step 8, and step 10 records an incomplete audit. On a new vault two such reasons are expected: `wiki/developments/known-issues.md` not yet created (CLAUDE.md's register rule recreates it) and no deep-lint entry yet in `wiki/log.md`; the audit stays incomplete, with its labels limited, until both exist.
   - **2:** stop the audit.
     - A `REFUSED: there is no slices.json` line is a continuity failure: the audit history and the baseline are gone. Restore the file from a copy. On a vault that has never run an audit it means only that Install has not run: run it. Never run `--init` again to get past it, since that starts the history over; with no copy, report the loss to the owner first.
     - A `REFUSED: slices.json could not be looked at` line is no continuity failure: the file may well be there, behind an error (a permission, say). Mend what it names and run again; never restore it or run `--init` on that line's account.
     - A `REFUSED` line about a malformed or unreadable `slices.json`: restore it from a copy, or mend what the line names, then run again. Never delete it.
     - A `PROBE FAILED` line names a broken premise, such as a required root (`.claude/`, CLAUDE.md, CUSTOMISATION.md, `wiki/developments/`, the tools folder or the hooks folder) that is missing or cannot be read, or could not be looked at; nothing is picked and no manifest is written. Mend that premise first.
   - **What no pick can see (the limit):** the lifecycle page, the register, CLAUDE.md, CUSTOMISATION.md and `wiki/log.md` are unframed Markdown, read by their structure alone (strict text, raw lines, whole tables, the register's two sections, deep-lint's entry with its two complete fields, and markdown-it-py's sections within the adapter's declared syntax), and no such page can show by its syntax that it lost only later material. So a cut that leaves a structurally valid shorter page cannot be told from the page alone, wherever it falls: rows or a whole table lost from the lifecycle page, sections lost from CLAUDE.md or CUSTOMISATION.md, the end of a register section, a later deep-lint entry, or fields after an entry's `Conflicts`. A section hidden by what a cut left open (a fence, a comment) is not that limit: the adapter cannot decide the file and refuses it, never a shorter list. The pick says so in the `limit:` line that ends its DUE ROWS, MISSING ROWS and SECOND-PASS SOURCES parts. The backstops: the hash scan, by which a page cut since the last audit reads as changed (CLAUDE.md and CUSTOMISATION.md then join the reading list, where the reviewer reads them; the lifecycle page and the register, held for the second pass, are named on a `held for the second pass (changed, read whole there)` line, and the register joins the reading list in its own week); and step 7's label check against the register, the only backstop for `wiki/log.md`, which is not hashed. Neither restores a row a cut took from the lifecycle page: a held line naming that page changed is the only sign of such a cut.
   - **Escaped lines:** a line that begins `escaped: ` held a character a terminal could hide (an escape, a right-to-left override, a newline in a file name). After that mark it is written with each such character as `\xHH`, `\uHHHH` or `\UHHHHHHHH` and every backslash doubled, as the `ESCAPED:` line above it says; reading the escapes left to right recovers the line. A reading-list path printed so is copied, and named under `## Not read`, as printed.

   The reading list's part `owed from an earlier audit` holds what earlier audits left unread (their pick could not read it, or their reviewer did not), and the `OWED` block names each entry and since when. Its files are read like the rest of the list, changed or not, and stay owed until the reviewer reads them (step 10). An entry's files held for the second pass (the register or the lifecycle page under a folder owed from an earlier audit, say) stay off the list, as every second-pass source does: the `OWED` block counts them, the second pass reads them, and the entry stays owed when the report names one of them (step 10). The part `deleted since its baseline, owed from an earlier audit` lists each owed path with no file of it left (gone, its absence established by its own metadata, or a folder there, listed whole, holding no file, printed with its trailing `/`), its root and every folder down to it read without failure: there is nothing to read, and the reviewer checks what still refers to it. A file deleted that was not owed is a `removed` line apart from the reading list, as before. The DUE ROWS block lists each due row, overdue first; a whole row the lifecycle page's rules do not allow (no Next review, no Retire when, a Kind or State outside its set, a Next review that is not a date, the wrong number of cells) is marked `MALFORMED` on its `due:` line, or listed under MALFORMED ROWS when it is not due, a finding for step 8. A retired row is never due, so it needs no Next review; its other checks stay. Read the `CONTROLS` line: the planted changes must read as caught.
2. **Name the run and the reviewer's folder.** Use run `run-<YYYYMMDD>-audit` and lane `RV-AUDIT` (the review naming convention):
   - the reviewer's working folder: `/tmp/run-<YYYYMMDD>-audit-RV-AUDIT`. Create it with `mkdir -p`. The reviewer writes nothing, here or anywhere;
   - the head's files: `/tmp/run-<YYYYMMDD>-audit`, made at step 1.
3. **Fill the brief.** Copy the fenced block of `<vault>/.claude/skills/weekly-audit/brief-audit.md` to `/tmp/run-<YYYYMMDD>-audit/brief-RV-AUDIT.md` and fill each slot from step 1's output:
   - **Reading list:** the READING LIST block whole.
   - **Due items:** the first line of each DUE ROWS entry, never its `due:` line, which can name a known fault.
   - **Unregistered items:** the MISSING ROWS entries.
   - **Pass-2 sources:** the `- ` lines of the SECOND-PASS SOURCES block, each whole, its marks included (`MISSING`, `UNREADABLE`, `UNKNOWN`): two when the slice is the register, which the first pass reads as its object and so is no second-pass source, three otherwise.
   - **Requirements:** the paths of the REQUIREMENT FILES block, each whole, or `none` when it lists none. The pick lists them by the slice (CLAUDE.md for every slice, `.claude/settings.json` too for the hooks and monitors, CUSTOMISATION.md for the standing rules, where both are on the reading list already), an absent one included (its note says so: keep it, and the reviewer names it under `## Not read`), and the record accepts each of them under `## Not read`. One whose path the reading list holds already, absent or not, is not repeated here: the reading list slot carries it.
   - **Variant:** delete the variant of PASS 1 step 2 that does not fit.

   Then the controls. Content controls search files, so they cover the reading list's existing files only: a path under the part `deleted since its baseline` holds no content to search, and is checked apart for nothing left to read.
   - **CONTROL+:** a phrase copied from one existing file of the reading list (never a path listed as deleted). Count it in that file with `grep -c -F` (1 or more).
   - **Negative control:** a fresh token from `python3 -c 'import secrets; print("na" + secrets.token_hex(8))'`. Search it with `grep -c -F` over every existing reading-list file, leaving out each path under `deleted since its baseline`. Every count must be 0; otherwise draw a new token.
   - **Deleted paths:** check each path under `deleted since its baseline` apart, for nothing left to read. The pick lists two kinds, so each path must pass one of two checks:
     - **an absent path:** `/bin/test ! -e <path>` succeeds;
     - **a folder there with nothing left to read** (listed with its trailing `/`): `/bin/test -d <path>` succeeds and `/usr/bin/find <path> ! -type d ! -name .DS_Store ! -name '*.bak*' ! -path '*/__pycache__/*' ! -path '*/node_modules/*'` prints nothing (the names every walk of the pick skips aside).

     A path that passes neither check holds something to read again, which makes the reading list stale: pick again (step 1).

   Last, search the filled brief for `{{`: there must be 0 hits. Its `CONTROL+:` line is the positive control and must hit once.
4. **Spawn the reviewer:** class critic, GPT-6 Astra at max, read-only: no `--write`, since the critic class writes nothing. The reason and the choice reason are recorded on its lane-open:
   `python3 -B <vault>/.claude/skills/delegate/codex-lane.py spawn --run run-<YYYYMMDD>-audit --lane RV-AUDIT --class critic --model gpt-6-astra --effort max --brief /tmp/run-<YYYYMMDD>-audit/brief-RV-AUDIT.md --cwd /tmp/run-<YYYYMMDD>-audit-RV-AUDIT --delegation multi --delegation-src head --reason "(a) the weekly fresh-eyes audit needs a reader uninvolved in the week's work, whose first pass holds no earlier answer (waste-reduction and retirement design, section 2)" --choice-reason "GPT-6 Astra at max: the reviewer section 2 of the design names for the weekly audit" --detach --no-wait`
   - **Exit 0:** prints `detached pid N`, and the worker outlives this call.
   - **Exit 2:** a premise failed and no lane started (for example a CONTROL+ phrase that does not hit). Mend it and spawn again. With no Codex CLI on this machine, spawn the same brief through the delegate skill's critic class instead; step 6's list then reads *unavailable*, by its table.
   - **Exit 4:** the start is unconfirmed. Go to step 5 anyway; the wait reports what happened.
5. **Wait for it.**
   - **Attended Sunday session:** one background wait that wakes the head once. Run, as a single background command:
     `python3 -B <vault>/.claude/skills/delegate/codex-lane.py wait --run run-<YYYYMMDD>-audit --lane RV-AUDIT`
     Then go on walking the calendar. Do not poll in between; the wait's exit wakes the head with the close line and the report.
   - **Hands-off run:** a hands-off head never ends its turn with a background job open. Instead it runs, in the foreground:
     `python3 -B <vault>/.claude/skills/delegate/codex-lane.py watch --run run-<YYYYMMDD>-audit --lane RV-AUDIT`
     It re-issues the watch after each exit 8 (still running) until the close (register entry of 2026-09-30 02:12).
6. **Check the plumbing, then read the list and write the outcome.**
   - The close is `completed`. The report is `<store>/spawn-records/run-<YYYYMMDD>-audit-report-RV-AUDIT.md`. It shows its CONTROL+ hit, a negative-token count of 0 over each existing reading-list file, and each deleted path confirmed to have nothing left to read: absent, or an existing folder whose reviewable listing is empty, as step 3 checks it. It ends with its `## Not read` section, closed by its `END NOT READ: <n>` line, which step 10 reads. Read that section now: any path it names (a reading-list file, a requirement file or a second-pass source) makes this audit incomplete at step 10, and when it names the register or `wiki/log.md` (a comparison source, which the labels rest on whichever pass reads it: in the register's own week the register is a reading-list file, read in pass 1, and what that pass read of it serves the labels), the labels are limited exactly as by step 1's `LABELS LIMITED` (step 7), however that source read at the pick.
   - List the reviewer's earlier commands from its run record:
     `python3 -B <vault>/.claude/skills/weekly-audit/pass_order.py --events <store>/spawn-records/run-<YYYYMMDD>-audit-events-RV-AUDIT.log`
     - **Exit 0, `COMMANDS BEFORE THE FIRST-PASS MESSAGE: <n>`:** the list: every command the reviewer started before its first-pass message, in the order each started, one entry per execution, each verbatim, then the count and the record's path. Verbatim is lossless: an entry with no character a terminal could hide prints byte for byte; an entry holding one prints in the encoding its header declares (`ESCAPED: <n> character(s) a terminal could hide written \xHH, \uHHHH or \UHHHHHHHH, and every backslash doubled`), so two different commands never print alike, and reading its escapes left to right recovers the command exactly. Its `boundary:` line names the message, the reviewer's first complete findings message under the brief's heading; the report's "Pass 1 findings" section repeats that message unchanged. File changes before the message, which a read-only reviewer should not make, are listed apart.
     - **Exit 1, `COULD NOT READ`:** the record cannot be read whole; each `could not read:` line names the record and the event's log line. There is no list.
     - **Exit 3, `NO FIRST-PASS MESSAGE`:** the record holds no complete first-pass message; `not a boundary:` and `near miss:` lines name the messages that came close. There is no list.
     - **Exit 2, `PROBE FAILED`:** an argument or an in-run control failed. Mend it and run again.
   - **Judge the list: one outcome, with a one-line reason.** Earlier answers are the known-issues register, earlier audit outputs (audit, review and run reports) and the withheld entries of a smoke test, whenever that file is not part of the week's slice. Read every listed command, decide what it read, and give the week the first outcome of this table that applies:

     | Outcome | When | The labels |
     |---|---|---|
     | *unavailable* | There is no list: the record could not be read (exit 1) or holds no complete first-pass message (exit 3). | Treated as not independent for labelling. |
     | *not independent* | A listed command reached earlier answers outside the week's slice. | The first pass's labels `new kind` and `new instance` are void, while each substantive finding the head verifies against the files themselves is kept, labelled by the head. |
     | *unresolved* | A listed command the head cannot judge from its text, such as inline code, a variable or a glob whose reads the text does not show. | Treated as not independent for labelling, with the reason recorded. |
     | *independent* | No listed command read outside the week's slice (its reading list and requirement files) or neutral material (a listing, a count, a file that holds no earlier answer). In a week whose rotating part is the register, reading the register is slice reading. | The labels stand as the reviewer gave them, subject to step 7. |

     *independent* is a source boundary only: a slice page that itself names earlier faults (a development page with its review record, say) is handled by the second pass's comparison, which labels such findings `known`.
   - **On frozen copies** (the procedure's smoke test), run the same command with `--whole-run`, which lists the commands after the message as well. The second pass is meant to read the frozen copies, so the question for each later command is not whether it read a second-pass source but whether it could have read the live file a frozen copy stands in for, the live register above all: one that did makes the outcome *not independent*, and one whose text does not show what it reads makes it *unresolved*.

   An outcome other than *independent* voids the labels `new kind` and `new instance`, never the findings. Record it as a finding about the audit itself.
7. **Re-verify each finding.** Open its cited `path:line` yourself and confirm the fault. Check its label against the register with a grep and its positive control. A finding that does not hold is recorded as refuted, with the reason. Under an outcome other than *independent*, label each finding that holds yourself, from the register and the files, never from the reviewer's `new kind` or `new instance`. When step 1 said `LABELS LIMITED`, or the report's `## Not read` names the register or `wiki/log.md` (step 6), no finding is recorded as `new kind`: each such label is a candidate you check against the register, recorded as `new kind (candidate)`. This label check against the register is also a backstop for the limit of step 1, and the only one for `wiki/log.md`, which is not hashed: a deep-lint entry lost to a cut that left the log structurally valid could have changed a label, and the register itself still shows the fault it recorded. The count of findings that hold is this audit's N for step 10.
8. **Dispose of each finding that holds,** by CLAUDE.md §12, "Act now if you can; park only with a reason":
   - **Fix now:** a certain fix within the owner's rules is made now, however long it is, on a helper where its length calls for one (§2.2's instrument rule). Each change is listed on its own, so it can be reverted alone.
   - **Register:** a fix waits only for a named blocker (his decision, a live run that owns the file, a missing grant or input). It is registered in `wiki/developments/known-issues.md` in the same pass, with that reason as its "why not fixed now" line. A finding labelled `known` already has its entry: add this audit's evidence to it rather than a second entry.
   - **Drop:** a finding not worth doing is said so and dropped, not registered.
   - **Ask the owner:** the rest is walked through with him in his decision pattern: the options, with a recommended pick. That covers a change to his rule text, a choice reserved to him, and a fix that rests on a guess.
   - **Due rows:** a keep, simplify, replace or retire proposal follows section 3's retirement rules:
     - a standing rule or text retires only on the owner's yes or by the §12 retire rule;
     - a whole script or file leaves only through the attic skill's preview and his yes (CLAUDE.md §2.1);
     - removing checks from a suite takes an independent review.
   - **Unregistered items:** each gets its row in the lifecycle register (the enrolment duty), unless a named blocker stops it.
   - **The rule register's one pass:** where `rule_register.py` stands beside this file, run `python3 -B <vault>/.claude/skills/weekly-audit/rule_register.py weekly`. It only lists, and takes seconds. Each line that needs action is disposed of as above, apart from the reviewer's findings and step 10's N. Once every line is disposed of, run `rule_register.py record-audit`, which records the fingerprints, rulings and listed flags the next pass compares with: a recorded flag is then only counted, unless its text changes, and `weekly --all-flags` lists every flag. Until it first runs, the pass says it has no baseline and lists every flag again.
9. **Record each disposition in the audit's own report:**
   `<vault>/output/reports/audit-report-<YYYY-MM-DD>.md`
   It holds:
   - the slice and the size of its reading list, and whether the pick was complete;
   - the owed list: each entry of step 1's `OWED` block, since when, how many of its files the reading list held and how many were held for the second pass (or `owed: none`);
   - the outcome of step 6 and its one-line reason, with the list's count: `outcome: <independent | not independent | unresolved | unavailable> · <reason> · <n> command(s) before the first-pass message`;
   - the coverage: the report's `## Not read` section, `none` or each path;
   - the counts line, `counts: new kinds k · new instances i · recurrences r · known n`, with `· candidates c` added when the labels were limited (step 1's `LABELS LIMITED`, or step 6's unread comparison source);
   - the cost, completed after step 10: the reviewer's tokens and time from its close line; the two usage readings, before step 1 and after step 10, with their times and each window's change between them; and the head's share. The Claude window's change is the head's share only when nothing else used that window between the readings; otherwise the head's share is written `unmeasured`, with that change as its upper bound. Any share the readings cannot separate (another lane in the same window, the calendar walk of the same session) is written `unmeasured`, never estimated;
   - the results of steps 1 and 6;
   - one row per finding: id · label · re-verified (held or refuted) · disposition (`fixed`, `registered`, `kept`, `owner` or `refuted`) · note (the change made, the register entry, the reason it was dropped, or the blocker).

   This table is the record of the audit's dispositions. The weekly waste report, run after this audit by CALENDAR.md's Sunday procedure, keeps its own figures' dispositions in its own store (`weekly-waste.py dispose`), which takes only the keys its reports list.
10. **Record the audit:**
    `python3 -B <vault>/.claude/skills/weekly-audit/slice.py --vault "<vault>" --record <slice> --findings <N> --manifest /tmp/run-<YYYYMMDD>-audit/manifest.json --report <store>/spawn-records/run-<YYYYMMDD>-audit-report-RV-AUDIT.md`
    - `<slice>` is the slice of step 1, the one its manifest names, and N is the count of findings that held at step 7. The record refuses any other slice before anything is written, and names the manifest's: the manifest's reading list, requirement files and second-pass sources are that slice's, so the record credits that slice alone, and the rotation counts as attempted only the slice the manifest represents.
    - It reads the report's last section, headed exactly `## Not read`, by the coverage protocol (Reading protocols): one path per line for each mandatory input the reviewer did not read in full (a reading-list file, a requirement file or a second-pass source), each with its exact characters (only the newline is removed, so a space a path ends with is part of it, and two paths that differ only so stay two), or the single word `none`, then its closing line `END NOT READ: <n>`, n the number of path lines (0 with `none`). Whitespace is forgiven only around the heading, `none` and the END line. A section that is missing, empty, names a path that is none of the mandatory inputs, holds any other line, puts `none` beside paths, lacks its `END NOT READ` line, carries a count that does not match its path lines, or holds anything after that line is refused with nothing written, and so is a report in which a second line declares `## Not read` or reads as a closing line, wherever it stands (a code block, a list, a quote or a comment too): a report cut after any whole line can never discharge what the cut removed. A requirement file or a second-pass source named there is owed nothing and is a reason the audit is incomplete (a second-pass source an owed entry holds keeps that entry owed: below); the register or `wiki/log.md` named also limits the labels (`LABELS LIMITED` in the record's output), in every week: in its own week the register is a reading-list file, owed when named like any other, and still a comparison source, a reason saying so. Coverage records the reviewer's declaration, not proof of what it understood. Never guess what the reviewer read: when its form alone is at fault (a bullet before each path, say, or a space added before a path), record from a copy of the report in the head's folder with only that form mended, each path then exactly as the reading list prints it. A missing or miscounted `END NOT READ` line is never a form to mend, since the report may be cut short: treat it as missing. When the section is missing or unclear, record from a copy whose `## Not read` section names every mandatory input of the pick, each as the pick printed it: every path line of its READING LIST block and of its REQUIREMENT FILES block, and the path on each `- ` line of its SECOND-PASS SOURCES block, closed by its count. The audit is then recorded incomplete with a reason for each omission, its labels limited (the register and `wiki/log.md` are among the paths named) and the whole reading list owed; say so in the report of step 9.
    - The audit is recorded complete only when its pick was complete and the section says `none`, and the record's own acquisitions (the premises, `slices.json`, the manifest and the report) all succeeded: the reviewer read every item of its slice, owed items included, every requirement file and every second-pass source. The `RECORDED` line says which; an `INCOMPLETE AUDIT` line says why, and each reason is stored with the audit in `slices.json`.
    - A `RECORD INCOMPLETE` line names a record's own acquisition that did not succeed. The record then moves nothing it cannot vouch for: with the report's coverage short (`coverage: UNKNOWN`), every reading-list file counts as not read and is owed; with any other short, `BASELINE KEPT whole` says the baseline did not advance and no owed entry was discharged. The rotation counts every recorded audit as attempted, complete or not, so the next pick moves on to another rotating part, while what this audit left unread is owed to every later reading list until the reviewer reads it.
    - The record writes the new state to a temporary file beside `slices.json`, reads it back and checks it, and only then replaces `slices.json` in one step. A read-back that does not succeed is a `REFUSED` line, and `slices.json` is unchanged. After that step nothing refuses: the `RECORDED` line stands, and the diagnostic rescan that follows cannot change the record (one that does not succeed is said, `UNKNOWN in part`). A `PROBE FAILED` line saying `slices.json was written` is never expected; it means the record is made, so check that file before anything else, and never restore it from a copy on that line's account.
    - The baseline advances only over what the audit read. Its `BASELINE KEPT` lines name each path kept at its earlier hash (`kept:`), whether its pick could not read it or the reviewer did not, or left out because it had none (`absent:`, so the next pick lists it as new). A file is kept by its place under its root, whatever spelling of the vault's path the pick or the record was given (its real path, or a link to it), so an omission never lets an unread file's hash into the baseline. A file changed after the pick (often by a fix of step 8) is not absorbed: the record lists it under "changed since the pick", and the next audit's pick lists it as changed, so a fresh reader sees each fix.
    - An owed entry is discharged (`owed: discharged`) only when this audit's pick listed its content and the reviewer read all of it, its files held for the second pass included: one of them named under `## Not read` keeps the entry owed and that file's earlier hash, whatever the week's phase; each other entry stays owed, and each path the reviewer did not read, or the pick could not, is newly owed (`owed:` lines, each with why). An owed path listed as deleted is discharged when the reviewer does not name it under `## Not read`, and the baseline then records it as absent, so its reappearance reads as changed; named, it stays owed with its earlier hash. A path is listed as deleted only when its absence is established by its own metadata, or when it is a folder whose listing, read whole, holds no file: one whose metadata could not be read, a symbolic link whose target is missing, or one that lies under a root or folder the pick could not read, is no deletion and stays owed. Copy these lines into the audit report.
    - A `REFUSED` line leaves `slices.json` unchanged: no `--manifest` or `--report`; a manifest taken over other roots; one taken before the last record (an old manifest, or this one recorded twice); one that is missing, unreadable or malformed; a report refused as above; an unknown slice, or any slice other than the one the manifest's pick chose (the line names that slice); the same slice already recorded today; or a new state that did not read back as written. A `PROBE FAILED` line before the record (a required root missing or unreadable) leaves it unchanged too.

## Quiet audits and cost

- **No quota.** The audit has no novelty quota, since a quota would reward relabelling.
- **Eight quiet audits:** eight in a row with no new kind of fault (set by judgement, unmeasured) trigger a review of the slice selection, the reviewer and the cadence in the Sunday walk-through, and the owner decides. Count them from the `counts:` lines of the audit reports. Only new kinds count: an audit whose findings are all new instances, recurrences or known faults is quiet. An audit whose labels were limited (step 1's or step 10's `LABELS LIMITED`) could not establish a new kind, so it is left out of the count, neither quiet nor not. Quiet audits never reduce the audit by themselves, and no slice leaves the rotation.
- **First four audits:** their measured cost, the reviewer's and the head's (step 9's cost lines, with `unmeasured` wherever the readings cannot separate a share), goes to the owner beside the findings it bought, with each week's list length and outcome from step 6, so he can judge proportion.
