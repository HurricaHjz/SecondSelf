# Disposable register views

`register-schema.json` is the closed structural contract. `adopt_data.py` applies the same structure plus cross-reference, route, ownership, reservation and proof-identity rules. `adopt_resources.py` verifies current resources and captured artefacts. JSON output is UTF-8, sorted keys, two-space indentation and one final newline; digests use compact sorted UTF-8 JSON with array order retained.

There is no independently writable manifest state. `adopt_manifest.py` exports a view carrying register ID, revision/data digest, row ID, expanded definition digest, actual caller model, qualification references and purpose. Consumers requery before use, after a model change and after any revision change. No view writes facts or falls back to an old file. Prepared delivery remains labelled; metadata compatibility preserves legacy descriptions without inventing qualification.

Evidence artefacts are strict JSON envelopes with `subject` and `result`. Resource and historical v1 task-check envelopes also carry `observation_sha256`, `positive_control`, `negative_control`, `criterion`, optional exact `output`, and `human_judge` for human assessments. The register stores their digests and typed locators. Checks use the shipped catalogue; data cannot supply executable checker code.

There are two explicit hash domains. An evidence subject's `definition_sha256` hashes `operational_definition()`: the expanded row, resources, installations, policy and evidence reference IDs. An activation/view `definition_sha256` hashes `expansion()`, which adds the complete referenced evidence records in ID order, including result, method, subject, artefact locator and artefact digest. Evidence does not hash itself recursively. Changing referenced evidence invalidates an active record; unrelated evidence does not. Every ordinary publication and journal recovery rechecks the qualification of each remaining active row. Earlier staged active proofs need fresh proof under this revised contract.

The operational definition includes an `installations` array containing the full definitions of every directly named installation and every installation reached through expanded resource ownership, sorted uniquely by installation ID. A direct installation remains included when it has no resources or its members are row-owned. Existing `/bindings/<index>/resource_definition` pointers stay unchanged. Changing any included pin invalidates activation; an unrelated installation's change does not. The prepared/active unresolved-pin gate uses this same complete installation set.

A historical v1 task-check envelope's `observation_sha256` hashes the typed `skill-qualification` projection: destination resource-definition digest, exact pin digest and complete observed skill-tree digest. It permits task evidence collected on separately staged candidate bytes to qualify those same installed bytes. Resource-check envelopes and activation observations retain full physical identities and are not converted into portable task evidence.

Maintenance plans may include `candidate_sources`, a closed list of `{resource_id, path, tree_sha256}` entries for affected skill trees. Sources are canonical, explicitly supplied and disjoint from the installation mutation scope and writer footprint. They do not replace destination locators in register facts. Assessment and pre-step checks read the staged sources; verified release re-evaluates the installed destinations with no source override, then leaves rows prepared. Every supervisor transition checks the reviewed plan digest, including final release.

Seed defaults and migration defaults disable both optional extensions. External launcher, update/install, setup/export and deep-lint cutover requires their supplied sources and exercised adapters. An obsolete Markdown reader or writer must not survive that cutover.

## Assurance version 2

The document and freshness rule versions are 2. `freshness.status` still records whether a skill exists in the closure; it is not a tier. Each exact-model comparison records `tier`, `proof_route`, `claim_evidence_refs` and ordered closed `events`. Event IDs are unique, timestamps are non-decreasing, and the evaluator derives every state transition. The row tier is the minimum in the explicit ordinal `unproven < claimed < proven`. An old task pass is retained as history and cannot promote. No-skill assessments return `status: not-applicable`, `tier: null` and empty skill/reference lists without a model prerequisite.

`evaluate()` returns `tier`, `skills`, `qualification_refs` and `control_hits`. Each skill includes candidate/release dates, date result/reason, proof route, valid evidence IDs, checked successes and their evidence IDs, threshold, last transition, last drop and current unproven reasons. `policy.how_to_successes_required` is a positive integer, default two, set by judgement, unmeasured. Booleans are not integers. `policy.owner_identity` defaults to null and is explicitly configured through the owner-reviewed writer.

Assurance uses a separate digest of `{kind: skill-assurance-v2, register_id, row_id, resource_id, resource_definition_sha256, pin_sha256, skill_tree_sha256, model_id, model_release_date, criterion, judge}`. It excludes task contents and mutable tier/history. A `skill-task` captured-source record contains the exact routed job definition, invocation, criterion and sorted unique named inputs with canonical base64 bytes. The canonical task digest binds the complete object. Both run envelopes, the comparison judgement and comparison event share the identical task ID, evidence ID and digest. The with-skill run precedes a distinct without-skill run; the captured task predates both. Integrity reading of a failed baseline is separate from the passing resource-proof reader.

Activation expansion traverses singular and list evidence references transitively, rejects missing/cyclic references, and deduplicates shared frozen tasks. It includes complete referenced records and policy, including the owner identity and threshold. Operational subjects remain separate to avoid recursive hashes. Changing an outcome, captured task, owner, rule, threshold or other bound fact invalidates the earlier activation/cache. Referenced artefact bytes are rechecked at delivery, publication and recovery.

Use views add `assurance_tier`, `assurance_basis`, `importance`, `testing_recommended`, `freshness_decision_refs`, `route`, complete `decision_records` and `owner_identity`. `importance` defaults to ordinary; important claimed work returns testing advice. Unproven decisions cover every unproven resource exactly once and name all current uncertainties, including any date failure. The request's `take-pattern` maps to stored `internalise`; the stored route enumeration remains unchanged. Views retain unproven labels when consent permits delivery. Acceptance-only views remain explicitly unqualified.

An `activate` change can supply `freshness_decisions`, keyed by selected row ID, with per-model `{model_id, route, freshness_decision_refs}` entries. The activation retains the verified coverage in its freshness evaluations. Maintenance plans can supply the same row mapping; candidate assessment and installed release both recompute it. Revoked consent or a new dependency refuses even when the installed bytes still match.

`record-freshness` is the typed append-only event writer; ordinary editing and reconciliation cannot replace its history. `upgrade-freshness` is the only explicit v1→v2 publication path. `adopt_compat_v1.py` and `register-schema-v1.json` retain the frozen validation/rendering boundary, including v1 reference resolution. Legacy rows and the Markdown migration preservation layer stay unchanged; the versioned coverage audit verifies the upgraded projection without manufacturing source facts. The pure upgrade leaves revision unchanged; the writer increments once and retains exact historical objects.
